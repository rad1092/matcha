## 화면 직접 확인

Libbet을 `load_rom({"sample":"libbet","frames":600})`으로 실행하면
소개 문구, 방향키/A 조작법, `Select: demo | Start: play`가 표시됐다.
`press({"buttons":["start"],"hold_frames":6,"wait_frames":120})` 뒤에는
컬러 타일·캐릭터·점수와 타이머가 있는 플레이 화면으로 전환됐다.
이때 상태는 CGB, 프레임 726, 에뮬레이션 시간 12.170초였다.
초기 60프레임은 도입 화면이므로, 조작서에 시작 메뉴까지 관찰하며 진행하는
절차를 명시했다. 시험용 PNG는 확인 후 삭제했다.

## 재현에 필요한 입력

- 기본 클라이언트: stdio JSON-RPC로 initialize → notifications/initialized → tools/list → tools/call.
- 상태 복원: save_state → run 90프레임(right+a) → load_state → state와 screenshot 비교.
- 쓰기 감시점: 임시 ROM의 0x0100에 `3E 2A EA 00 C0 18 FE`를 배치하고
  0xC000 쓰기 감시점을 설정. 0x0102의 명령이 0x2A를 기록한 직후 정지했다.
- RAM 검색: find_value start → write_memory C000=[99] → changed 필터.
  결과는 `1 candidate address(es): $c000=99`였다. 저장 복원 뒤 값은 0x2A로 복구됐다.
- 저장 슬롯 수명: 새 ROM 로드 후 이전 슬롯 복원을 요청해 오류 반환을 확인했다.
- 실패 정리: 빌더만 복사한 임시 소스에 이전 ZIP을 두고 실행. 입력 누락으로 실패한
  뒤에도 이전 ZIP 바이트는 같았고 임시 스테이징 폴더는 남지 않았다.

임시 합성 ROM은 카트리지 타입 ROM-only, 32 KiB, 컬러 지원 헤더를 사용했다.
합성 ROM SHA-256: `89c34ef75c04fed471998b0a705b752da75bced887354cd5f327c48ee8012753`. 원본 샘플은 수정하지 않았다.


## 검증 중 수정과 범위

첫 임시 시험은 쓰기 감시점 응답에 `watchpoint`라는 단어가 있을 것으로 가정해
실패했다. 실제 응답은 `instruction at $0102 wrote $2a to $c000`으로 정확한
쓰기 위치·값을 보고했다. 임시 시험의 기대 문구를 실제 응답 형식에 맞춘 뒤
전체 13개 묶음이 통과했다. 이 문제로 제품 런타임 코드를 변경하지 않았다.

마지막 수정은 도입 화면을 기다리는 조작서 설명뿐이었다. 두 패키지를 다시
만들고 최종 문서·설정·런타임이 소스와 일치하는지, SHA256SUMS가 맞는지
확인했다. 실제 시험한 런타임과 최종 런타임의 바이트도 일치한다.

특정 AI 앱의 실제 연결, Node 18/다른 OS에서의 실행, 모든 게임의 호환성은
이번 시험 범위에 포함하지 않았다. 범용 MCP 클라이언트로 프로토콜과 도구를
검증했다. Rust 코어와 WASM 바이너리는 수정하지 않았으므로 CPU 전체·ROM
적합성 시험을 다시 돌리지 않았고 기존 호환율을 새로 검증한 것으로 표시하지 않는다.

## 정리

- 시험 클라이언트·화면 확인 코드·추출 패키지·복사 및 합성 ROM·PNG·임시 로그·시험 결과 JSON을 포함한 전용 임시 폴더 삭제 완료.
- 시험에서 생성한 Node 서버 프로세스 잔존 0개 확인. stdin EOF에 따른 정상 종료도 별도 검증.
- 시험 코드·이미지·ROM을 저장소에 추가하지 않음. 이 텍스트 기록과 배포 산출물만 보존.
- 기존 테스트 소스, 사용자 ROM·저장 데이터, 기존 분석 결과는 보존.
